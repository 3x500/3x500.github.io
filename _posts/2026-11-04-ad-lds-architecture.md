앱의 사용자 프로필과 확장 속성을 LDAP로 제공해야 하지만 AD DS Forest 스키마를 바꾸고 싶지 않은 경우가 있다. AD LDS는 이런 앱 전용 디렉터리 요구를 검토할 선택이다. 원본 LDS 문서의 도입·사전 준비·아키텍처 장을 바탕으로 무엇을 분리하고 무엇을 별도로 운영해야 하는지 정리한다.

## AD DS와 다른 운영 단위

| 요구 | AD DS | AD LDS 설계에서의 판단 |
|---|---|---|
| 도메인 가입·Windows 인증·GPO | 도메인 인프라 제공 | 앱 디렉터리만으로 이 기능을 대체하지 않음 |
| 앱 전용 LDAP 데이터 | 기존 스키마·권한·서비스 영향 검토 | 앱별 파티션·스키마·권한을 별도로 운영 |
| 독립 디렉터리 여러 개 | Forest·Domain 설계 영향 | 서버 한 대에 여러 인스턴스 가능. 포트·경로·계정·자원 충돌 관리 |
| AD 계정 연동 | 도메인 계정·Trust·인증 경로 | Windows 신원 사용·객체 동기화·Bind Proxy를 각각 설계 |

AD LDS는 독립된 앱 디렉터리 서비스를 제공하며 AD와 공통 API·LDAP 관리 개념을 활용한다. 앱의 인증·권한과 계정 수명주기 책임까지 없어지는 것은 아니다. [AD LDS의 목적](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/adam/active-directory-lightweight-directory-services)

## 서버·인스턴스·복제 집합·파티션

```text
LDS01                        LDS02
 AppDirectory 인스턴스  ←→   AppDirectory 복제 인스턴스
   Configuration / Schema      같은 복제 집합의 공통 정의
   DC=app,DC=example,DC=com     참여하도록 지정한 앱 파티션

LDS01의 별도 인스턴스         별도 포트·서비스·DB·구성 집합
```

같은 서버의 두 인스턴스와 다른 서버의 복제 인스턴스는 다르다. 독립 생성한 인스턴스가 같은 파티션 이름을 쓴다고 자동으로 같은 복제 집합에 들어가지 않는다. 가용성이 필요하면 서버·호스트·스토리지 장애 도메인과 앱의 접속 전환까지 설계한다.

| 파티션 | 역할 | 복제·변경 범위 |
|---|---|---|
| Configuration | 인스턴스·복제 등 구성 메타데이터 | 복제 집합의 공통 구성 |
| Schema | 클래스·속성 정의 | 같은 복제 집합의 스키마 영향 |
| Application | 앱 사용자·그룹·프로필 등 | 앱별 Naming Context와 복제 참여 대상을 결정 |

앱 데이터는 애플리케이션 파티션에 저장한다. 최초 구성 시 스키마·구성 파티션이 생기지만 앱 파티션 생성은 나중에 할 수도 있다. 인스턴스 서비스가 실행 중이라는 사실만으로 필요한 앱 파티션까지 준비됐다고 보지 않는다. [앱 파티션 생성과 데이터 저장](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/adam/using-application-directory-partitions)

## 원본 포트 설정 화면을 설계표와 연결한다

![원본 LDS 인스턴스 마법사의 LDAP 389·SSL 636 입력 화면]({{ '/images/ad-deep-dive/d-017.png' | relative_url }})

원본 화면은 LDAP 389·SSL 636 입력값을 보여준다. TLS 연결 성공이나 인증서 설치를 증명하지 않는다. 아래 설명용 설계에서는 기존 서비스와의 충돌을 피하기 위해 50389·50636을 예로 들며, 화면의 실제 설정을 바꿔 표시한 결과가 아니다.

| 설계 항목 | 설명용 값·선택 | 선택 이유·검증 |
|---|---|---|
| 인스턴스 | `AppDirectory` | 서비스·운영 책임을 식별. 서비스 이름은 설치 결과로 확인 |
| Endpoint | `LDS01.ad.example.com:50389` | 해당 인스턴스의 LDAP 포트. 서버·다른 인스턴스와 충돌 검사 |
| TLS Endpoint | 같은 FQDN의 50636 | 별도 인증서·개인키·신뢰·실제 TLS 검사 |
| 앱 파티션 | `DC=app,DC=example,DC=com` | 앱 Base DN과 일치. DNS 영역을 만든다는 뜻은 아님 |
| 데이터·로그 | 승인된 서버 경로 | 용량·권한·백업·I/O·디스크 장애 영향 |
| 복제 | 별도 서버와 필요한 앱 파티션 | 역할·포트·계정·복제 상태와 앱 전환 검사 |

포트 쌍을 정했다고 복제용 통신까지 모두 준비된 것은 아니다. 앱 연결, 관리 접속, 복제의 출발지·목적지·인증·RPC 조건을 따로 기록한다. 방화벽 규칙도 필요한 구간만 허용한다.

## 서비스 신원과 앱 신원을 분리한다

원본의 서비스 계정·관리자 계정·Bind 계정 구분을 인수 항목으로 사용한다.

| 신원 | 책임 | 과도 권한을 막을 기준 |
|---|---|---|
| Windows 서비스 실행 계정 | 인스턴스 프로세스·파일·키·인증 경로 | 서비스에 필요한 권한과 키 읽기만 검토 |
| LDS 관리자 | 구성·스키마·인스턴스 관리 | 앱 조회 계정으로 재사용하지 않음 |
| 앱 Bind 신원 | 앱 데이터 조회·승인된 수정 | 파티션·객체·속성·작업을 제한 |
| 동기화 신원 | 원본 읽기·대상 갱신 | 방향·범위·삭제·재시도와 승인 관리 |

원본의 gMSA 사용 권고는 AD LDS 서비스의 실제 OS·설치 방식·제품 지원을 확인하지 않고 일괄 적용하지 않는다. 19편의 일반 서비스 gMSA 지원과 이 인스턴스의 지원을 같은 증거로 취급하지 않는다. 검증한 서비스 계정 방식과 회전·복구 절차를 선택한다.

## 설치 전에 정할 인수 기준

앱의 객체·속성·검색량·쓰기 패턴·허용 지연을 수집하고 용량·인덱스·복제·백업을 설계한다. 원본의 CPU·메모리·여유율 예제는 실측 용량 보장으로 사용하지 않는다. 도입 여부는 AD DS 기존 속성 활용, 앱 자체 저장소, 별도 LDS 운영 비용을 비교해 정한다.

검증표에는 역할 설치, 인스턴스 서비스, 파티션·스키마, TLS, Bind·Search, ACL, 복제, 앱 전환, 복구를 각각 남긴다. 설치 화면의 완료만으로 앱 디렉터리 도입을 완료 처리하지 않는다.
