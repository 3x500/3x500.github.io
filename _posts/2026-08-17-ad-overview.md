직원이 입사할 때마다 PC와 파일 서버에 계정을 따로 만든다고 생각해 보자. 비밀번호 변경과 퇴사자 권한 회수도 각각 처리해야 한다. 장비가 늘수록 누락을 찾기 어려워진다.

Active Directory Domain Services(AD DS)는 사용자·컴퓨터·그룹 등의 정보를 디렉터리에 저장하고, 도메인 인증과 중앙 관리의 기반을 제공한다. 회사의 계정 명부에 인증 기능을 연결한 시스템으로 이해하면 출발하기 쉽다. 다만 단순한 연락처 목록과 달리, 계정과 권한에 연결되는 보안 정보까지 다룬다. [Microsoft AD DS 개요](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/virtual-dc/active-directory-domain-services-overview)

## 계정 관리에서 달라지는 점

| 작업 | 장비별 로컬 계정 중심 | 도메인 계정 중심 |
|---|---|---|
| 사용자 관리 | 각 장비에서 별도 관리 | AD 사용자 계정을 기준으로 관리 |
| 리소스 접근 | 장비마다 계정·권한 조정 | 그룹과 리소스 권한을 연결 |
| 단말 설정 | 장비별 설정 | GPO 등으로 대상별 정책 관리 |

AD를 도입해도 로컬 계정은 남을 수 있다. 모든 업무 시스템이 자동으로 AD 인증을 사용하는 것도 아니다. 어떤 시스템을 연동하고 어떤 계정을 예외로 유지할지 운영 범위를 정해야 한다.

## DC가 하는 일

Domain Controller(DC)는 AD DS를 실행하며 디렉터리와 인증 서비스를 제공하는 서버다. 여러 DC를 운영하면 데이터를 복제해 가용성을 높일 수 있다. DC를 여러 대 두는 것과 별도 백업을 보관하는 것은 목적이 다르다. 잘못된 변경도 복제될 수 있기 때문이다.

이 글에서는 가상의 `ad.example.com` 도메인과 `DC01`, `DC02`를 예로 사용한다. 실제 운영 환경을 공개한 이름이 아니다.

## 인증과 권한은 구분한다

사원증으로 신원을 확인했다고 모든 방에 들어갈 수 있는 것은 아니다. 인증은 누구인지 확인하는 과정이고, 권한 검사는 해당 리소스에서 무엇을 할 수 있는지 판단하는 과정이다.

파일 서버에 로그인한 계정이 확인돼도 공유·파일 권한에 따라 접근이 거부될 수 있다. 그래서 “로그인은 되는데 파일을 못 연다”는 문제를 무조건 비밀번호나 DC 장애로 처리하지 않는다. 그룹 멤버십과 리소스 ACL도 확인한다. [Microsoft 접근 제어 개요](https://learn.microsoft.com/en-us/windows/security/identity-protection/access-control/access-control)

## 원본 설계도를 운영 책임으로 읽는다

![원본 구축 문서의 Single Domain 설명용 아키텍처]({{ '/images/ad-deep-dive/a-003.png' | relative_url }})

이 그림은 구축 문서의 설명용 아키텍처이며 실제 운영 성공 화면은 아니다. 그림의 “500명 미만”은 원본의 설계 사례이고 AD의 용량 제한이 아니다. `GC / Backup` 표기는 두 번째 DC가 별도 백업을 대신한다는 뜻으로 사용하지 않는다. FSMO 역시 모든 역할을 반드시 분산해야 하는 규칙이나 자동 대기 전환 구조가 아니다. 두 DC의 역할, 장애 도메인, 별도 백업·복구 책임을 설계서에 명시한다.

| 구성 | 데이터·요청의 흐름 | 운영 인수 기준 |
|---|---|---|
| DNS | 단말이 서비스 후보 이름과 주소를 찾음 | 내부 영역·SRV·질의 경로를 서버별 확인 |
| DC·인증 | 계정과 인증 요청 처리 | 대표 사용자·컴퓨터의 인증과 실패 로그 확인 |
| 그룹·리소스 | 그룹 정보를 바탕으로 리소스가 접근 판단 | 승인 사용자 허용과 비승인 사용자 거부를 함께 검사 |
| GPO | 디렉터리 정보와 SYSVOL 정책 파일을 단말이 처리 | 대상별 결과 보고서와 실제 설정 확인 |
| 복제 | DC 사이에서 파티션 데이터를 전달 | 파트너·파티션·마지막 성공·오류를 확인 |
| 백업 | 독립 보관한 복구 지점으로 과거 상태 복원 준비 | 복구 목표·보관·격리 복구 시험 기록 |

원본의 “DC 최소 2대”는 가용성 요구를 위한 설계 기준이다. 수량만 채워도 전원·호스트·관리 계정·백업이 함께 손상되면 서비스와 복구가 모두 영향을 받는다. 표의 각 항목마다 담당자, 관찰 위치, 실패 시 연락·중단 기준을 지정한다.

## 구축 완료를 판단할 조회와 테스트

AD 관리 모듈이 있는 관리 PC에서 디렉터리를 읽을 수 있는 계정으로 다음을 조회한다. `DC01`은 가상 대상이다. 실제 출력은 수집하지 않았다.

```powershell
Get-ADRootDSE -Server DC01 |
    Select-Object dnsHostName, defaultNamingContext, configurationNamingContext, schemaNamingContext
```

예상한 서버·도메인 파티션인지 확인한다. 이 조회는 디렉터리 정보 접근의 증거이며 사용자의 Kerberos 인증, GPO 적용, 파일 권한까지 검증하지 않는다. [Get-ADRootDSE](https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-adrootdse)

| 테스트 | 성공 관찰 | 실패했을 때 분리할 범위 |
|---|---|---|
| 내부 이름·DC 검색 | 의도한 영역에서 실제 후보를 찾음 | 클라이언트 DNS·영역·SRV·통신 |
| 대표 계정 로그인 | 온라인 도메인 인증과 대상 서비스 접근 | 캐시 로그온 여부·인증과 권한 |
| 정책 파일럿 | 결과 보고서와 실제 값이 일치 | 링크·필터·클라이언트 처리·SYSVOL |
| 권한 회수 | 신규 세션에서 회수 대상이 접근 거부 | 중첩 그룹·토큰·기존 세션·리소스 ACL |
| 복구 연습 | 격리 환경에서 지정 복구 지점과 서비스 검증 | 백업 유효성·의존 서비스·복구 순서 |

문제가 생기면 영향 단말·계정·서비스와 변경 시각을 먼저 좁힌다. 설치 직후 정상이라는 이유로 운영 장애에서 도메인 재구축을 첫 조치로 삼지 않는다. 새 정책·권한 변경이 원인이라면 기록한 변경을 되돌리고 같은 허용/거부 테스트를 다시 수행한다. 도메인 이름·구조·스키마 같은 변경은 별도 이관·복구 계획이 필요하다.

## 운영에서 먼저 정할 것

도메인 이름보다 먼저 관리할 대상과 책임 범위를 정한다. 사용자·PC·서버를 누가 관리하는지, 입사·이동·퇴사 시 권한을 어떻게 바꾸는지, 장애가 나면 무엇을 복구할지 정리해야 한다.

AD 구축의 완료 기준도 역할 설치 성공만으로 잡지 않는다. 사용자 인증, 정책 적용, 리소스 접근, 복제, 복구 준비를 각각 확인해야 운영 가능한 상태에 가까워진다.
